桌宠卡在加载中：一次 CSP 与跨设备调试复盘

浏览器 · CSP · 跨设备调试

我和编码助手给 PetApp 桌宠 做了一个“带走”功能：把链接拖进书签栏，以后在其他网页点一下，宠物就出现在页面上。它可以被摸头、喂食，也可以拖到角落。原本只是想让小工具更方便，却遇到了一个很容易过早宣布修好的问题。

助手在开发机的 Google 页面上测试通过，我在另一台设备试，却一直看到“小伙伴正在赶来”。后来换到 X，截图中出现了损坏的页面图标。最后确认的原因是：旧版把桌宠放进外部 iframe，X 页面自己的 CSP 不允许加载这个来源。修复改成了自包含书签，2026 年 10 月 17 日，我在另一台设备上确认可用。

真正值得留下的，是从“我这里能跑”走到这个结论，中间漏掉了什么。

先问清楚，究竟是谁嵌入谁

旧结构很直观：书签在当前页面插入一个浮动容器，再加载本站的 companion.html。宠物在 iframe 内运行，父页面负责拖动和关闭，两边通过 postMessage 通信。页面和素材集中托管，书签本身很短，更新也方便。

看到 Google、跨域、iframe 几个词，助手最初把注意力放到了 X-Frame-Options 上，解释成“Google 不允许被别的网站嵌入”。这把方向搞反了：我们没有把 Google 装进桌宠页面，而是要把桌宠装进 Google 或 X。

要判断的问题主要看什么
当前网页允许加载哪些 iframe？宿主的 CSP frame-src，以及其回退规则
桌宠响应允许被谁嵌入？桌宠响应的 frame-ancestors / X-Frame-Options
脚本能否读取跨源请求的响应？相应请求的 CORS 规则

这些机制都可能和“跨域”同时出现，却控制不同的事。MDN 对 frame-src 和 X-Frame-Options 的说明，最有用的地方正是方向。方向没有弄清，换域名、调请求头，都可能改不到真正生效的那一端。

控制台里，最红的报错未必最接近根因

从失败设备取回的日志里，有遥测请求被客户端拦截，也有浏览器扩展相关错误。这些值得保留，但不能直接认定它们让桌宠失败。一个网站自己的统计请求失败，和我们的 iframe 没加载，是两条不同的链路。

跨设备排查的第一步，是把失败设备的证据带回来。截图告诉我们停在哪一层，控制台日志给出具体错误，响应头说明浏览器正在执行什么限制。助手可以在开发机检查代码，但不能用开发机的日志替代另一台机器上的现象。共享材料只需保留与失败有关的片段，发布复盘前还要去掉账号、页面内容和地址中的私密信息。

另一个显眼错误来自 postMessage：发送时期待接收窗口位于 https://tech.wenmq.cn，实际看到的接收方 origin 却是 null。这说明接收窗口没有处在预期状态，可能还未导航完成，也可能根本没能载入。它提供了线索，尚未解释为什么没载入。postMessage 的 targetOrigin 匹配不能代替导航诊断，把目标改成 * 也不会让被拦截的页面出现。

助手的第一版修复围绕这些症状展开：收到可信的 ready 握手后再通信，插入前先设置地址，增加超时、重试，并清理拖动状态。这些改动处理了时序问题，本机 Google 的测试也通过了。但我在另一台设备重试仍失败，说明这份验证没有覆盖真正的失败条件。我要求继续查清原因，不能再让本机测试替代失败环境。

超时和握手仍然有价值：网络慢、导航未完成时，界面不该失去回应。但它们只能让失败更可控，不能改变宿主允许加载的来源。把“错误提示消失了”和“加载链路成立了”分开看，才能决定下一步继续修通信，还是回到 iframe 导航本身。

决定性的证据来自 X 的响应头和浏览器的策略违规日志：它的 enforced CSP frame-src 白名单里没有本站；插入旧桌宠 iframe 时，浏览器明确报告 framing 被该指令拒绝。外层按钮仍可出现，内层页面却根本进不来，于是留下了永远等不到完成的加载状态。

这里直接确认的是 X 的 iframe 拦截；最初 Google 场景的全部失败原因，没有足够证据逐一归因。

这也解释了为什么单独访问桌宠地址、看到 HTTP 200，不足以证明嵌入可用。服务器可以正常提供页面，宿主浏览器仍会在加载链路上拒绝它。至于 GitHub Pages 在另一网络是否可达，是另一个需要证据的问题，不能拿它替代这次已经确认的策略原因。

修复落在结构上：把运行所需的东西带进去

既然宿主不允许这个外部 iframe，继续给 iframe 加重试就没有意义。我们把方案改成：书签携带渲染代码和图片，直接在当前页面挂载桌宠；代码改动与自动化验证由助手执行，我继续在另一台设备复测。

旧：书签 → 外部 iframe → 桌宠页面 → 渲染器与图片
新：书签内的 IIFE ＋ 内嵌图片 → 当前页面中的 Shadow DOM → 桌宠

这里没有重新画宠物或简化动作。原来的 Three.js / GSAP 运行方式继续使用；48 帧 PNG 的内容、顺序和播放参数保留，按文件字节去重后是 42 张独立图片。构建时将图片编码成 Data URL，连同渲染代码打包。召唤时不再请求外部 iframe、脚本或图片。

宠物本身只增加了资源地址注入。下面是实际提交代码的节选，省略了无关初始化：

export function createMaodiePet({ assetUrls = {} } = {}) {
  // …省略初始化
  function loadTex(p) {
    const t = texLoader.load(assetUrls[p] || BASE + p);
    t.colorSpace = THREE.SRGBColorSpace;
    return t;
  }
  // …省略动作和生命周期实现
}

普通页面仍可使用原路径，书签则传入内嵌图片映射。这样把“资源从哪里来”从动作代码中拿出来，不必复制第二套宠物实现。对应的宠物源码和构建插件都有固定版本可查。

封装成书签的核心也很短，真正大的部分在构建产物里：

const code = `void function(){${portableSource}\nPetAppPortable.install(${JSON.stringify({ pet, locale })})}()`;
const bookmark = `javascript:${encodeURIComponent(code)}`;
if (bookmark.length > 1900000) throw new Error('Portable pet bookmark exceeds the supported URL size');

这段摘自书签生成器。Shadow DOM 用来隔离页面与桌宠的样式，它不绕过 CSP。宿主如果禁止内嵌图片、限制显示样式，或者设备没有可用的 WebGL，仍然可能失败。

网络依赖少了，代价不能藏起来

新书签有 1,467,580 个 ASCII 字符，对应同样数量的字节，约 1.47 MB。重复图片去重能减小体积，但把运行时和素材带走，必然比一个 iframe 地址重得多。

实现中为生成结果设置了 1,900,000 字符的保护阈值，避免素材无意增长后静默生成过大的地址；这不是所有浏览器都认可的兼容承诺。独立配置中已经验证了书签 API 能精确保存并读回当前地址，但 Chrome Sync、其他同步服务和各类浏览器的完整链路没有普遍验证。已保存的自包含书签也不会自动得到新代码，更新需要重新保存。

此外，去掉 iframe 后，桌宠和宿主处在同一个页面，输入事件更要收束。拖动结束、窗口失焦、关闭时都要清理状态；透明区域应继续把点击交给原网页，不能让一块看不见的画布挡住阅读。运行时复用原动作，关闭时释放资源，异步初始化设置 10 秒超时。已识别的图片、样式或图形失败会给出说明和重试、关闭入口，不能继续显示“正在赶来”。

这部分工作没有改变宠物长什么样，却决定它能不能作为挂件长期待在别人的页面上。

跨设备验证，要拆成几种不同的证据

这次之后，我要求验收提供更多证据。助手把回归搬到独立的 Windows 和 Linux 机器，每个平台运行 9 组检查；同时保留清洁源码的构建检查，避免本地未提交文件混入结果。

设备和站点也要分别改变。只换设备，可以发现缓存、配置或网络差异，却未必覆盖另一个网站的策略；只换网站，可以暴露不同响应头，却仍共享开发机状态。因此可控测试页负责固定限制，外站负责检查真实环境，独立机器负责减少本地条件的干扰。这几层合起来，才比多截几张本机成功画面更有说服力。

其中最重要的是一个受严格 CSP 保护的测试页面。页面禁止外部 iframe 和网络连接，允许此次需要的内嵌图片。先插入旧 iframe，确认它确实被拦，证明测试没有悄悄放开安全策略；再让页面断网，执行新书签。检查的不只是容器出现，还包括 WebGL 有真实像素、动作按钮有回应、可以拖动、拖完后的空白区域能点击原网页，以及关闭后实例被清理。

失败用例同样保留：禁止图片、禁止样式、关闭 WebGL，应该进入明确失败态；减少动态效果时先暂停，允许手动开启。还检查窄屏边界、多实例，以及初始化未完成就关闭的情况。

这些检查通过 CDP Runtime.evaluate 执行完整序列化的书签代码，带用户手势，没有关闭 CSP。这能检查代码和策略的关系，仍不等同于真人从主页拖出、保存，再从书签栏点击的全流程。独立配置里的书签保存读回也是另一项证据，两者都不能自动推导出跨设备同步成功。跨平台回归记录与清洁源码检查分别保留。 具体断言和运行环境可对照测试脚本与CI 工作流。

外站检查也要写清页面状态。CI 访问 X 时收到 HTTP 403，返回页带真实 CSP，桌宠在这张返回页上渲染成功；不能把它写成“已通过登录后 X 时间线全流程”。Godot 则使用官方的 godotengine.org，该页返回 200，桌宠正常渲染。godot.com 是停放域名，域名相像不能当成同一个测试对象。

最后还要确认实际拿到的是哪一版。修复发布后，助手从线上页面读出真实书签，在独立 Ubuntu 环境重新跑检查，而不是复用本地构建；57 个发布产物逐项 SHA-256 回读一致。生产书签回归记录对应源码 6d4b340，站点发布版本为 3155eab。我随后在另一台设备确认可用，才补上了最初那份本机测试没有提供的使用证据。没有记录到的系统和浏览器版本，也不替它补写。

下一次，我会更早要求哪几条证据

再遇到同类问题，我会先画出宿主、子页面、脚本和图片之间的加载关系，再去判断是哪条策略、哪次导航或哪个资源失败。控制台里与工具无关的错误单独记录；null origin 这类现象继续向上追，不提前当成根因。

验证也要跟着原报告走：失败发生在哪个站点、哪台设备，就不能只用开发机上的另一个站点收尾。可控页面用来固定策略和做负对照，独立机器用来排除本地状态，线上书签回读用来确认交付内容，实际使用者的重试用来确认原场景是否恢复。每一项回答自己的问题。

这次需要保留下来的判断很具体：宿主拒绝外部 iframe 时，应重新考虑依赖这个 iframe 的结构；而在说“修好了”之前，必须拿到能够覆盖原失败条件的证据。
